# ADR 0001: Стиль архітектури — модульний моноліт

- **Статус:** Прийнято
- **Дата:** 2026-11-21

## Контекст

- Проєкт Zhuzhyk — навчальний командний онлайн-магазин, у якому працює невелика команда студентів.
- Поточний стек: Node.js + Express, SQLite, статичний HTML-клієнт. Одна кодова база, одна БД, один процес.
- Доменна модель (практична 3) виділяє контексти Catalog, Orders, Users, Payments, Delivery, але більшість із них ще не реалізована.
- Docker, CI/CD та спостережуваність з'являться лише в наступних практичних; поки що немає інфраструктури для запуску багатьох сервісів.
- Команда невелика, окремих команд на кожен контекст немає, навантаження мінімальне.

## Рішення

Продовжуємо як **модульний моноліт**: один застосунок і один процес, у якому код розділений на логічні модулі за шарами (`api/`, `service/`, `domain/`) і за контекстами (Catalog — перший, далі Orders, Users…). Контексти спілкуються через виклики сервісів у коді, а не через мережу.

## Розглянуті альтернативи

**Мікросервіси (пілот).** Плюси: незалежні релізи та масштабування, чіткі межі даних. Мінуси для нашого стану: мережеві виклики між сервісами, розподілена консистентність, складніший запуск і налагодження, потреба в Docker/оркестрації ще до того, як ми їх вивчили; виграш від незалежного масштабування для навчального проєкту нульовий. Відхилено.

**Моноліт без модульності («грудка»).** Швидше на старті, але шари змішуються, і пізніше виділити контекст буде дорого. Відхилено.

## Наслідки

- Один репозиторій, одна збірка, один запуск (`npm start`); просте відлагодження та тестування.
- Один процес і одна БД: масштабується лише весь застосунок, а збій одного модуля може вплинути на весь процес.
- Межі модулів тримаються дисципліною (правила в ADR 0002), а не мережею — їх треба захищати на code review.
- Контексти не повинні звертатися до таблиць одне одного напряму, лише через сервіси. Тоді згодом контекст можна буде винести в окремий сервіс.
- Рішення не заважає наступним практичним: Docker-образ один, у CI одна збірка, у Kubernetes один Deployment.

## Умови перегляду

Повертаємося до питання мікросервісів, якщо:
1. з'являються окремі команди або суттєво різний темп релізів для контекстів (наприклад, Payments);
2. один контекст потребує незалежного масштабування або іншого стеку;
3. зміни в одному модулі регулярно ламають інші попри чіткі шари;
4. після практичних із Docker і Kubernetes команда готова підтримувати кілька сервісів, а виділення має очевидну користь.
