# ADR 0002: Шарова структура бекенду

- **Статус:** Прийнято
- **Дата:** 2026-11-21

## Контекст

Після вибору модульного моноліту (ADR 0001) потрібні прості правила, що де лежить і хто кого може викликати. Інакше SQL, валідація та HTTP-логіка змішаються в `server.js`, як було в практичній 1.

## Рішення

Структура `backend/`:

```
backend/
├── server.js        # composition root: збирає шари та запускає сервер
├── app.js           # створення Express-застосунку (middleware, маршрути)
├── api/             # HTTP-шар
├── service/         # use-cases та валідація
├── domain/          # сутності та інваріанти
├── repository/      # доступ до SQLite
└── test/            # юніт-тести service/
```

| Шар | Що зберігається | Чого там немає |
|---|---|---|
| `api/` | Express-роути й контролери: приймають запит, передають тіло/параметри в service, повертають відповідь і статус за контрактом OpenAPI; `errorHandler` перетворює помилки service на HTTP-відповіді | бізнес-логіки, валідації, SQL |
| `service/` | Use-cases (`ProductService`), валідація вхідних DTO, мапінг DTO ↔ domain, помилки `ValidationError` / `NotFoundError` | Express (`req`/`res`), статус-кодів, SQL |
| `domain/` | Сутності (`Product`, `Order`) та їхні інваріанти | залежностей від інших шарів, HTTP, БД |
| `repository/` | Єдине місце з SQL: `SqliteProductRepository`, відкриття БД і міграція | бізнес-правил, HTTP |

### Напрямок залежностей (зверху вниз)

```
api  →  service  →  domain
              ↘ (через інтерфейс, передається ззовні)
                repository
```

- `api/` залежить від `service/` (та його класів помилок).
- `service/` залежить від `domain/`. З репозиторієм працює через об'єкт, який отримує в конструкторі, і не імпортує `better-sqlite3`.
- `domain/` не залежить ні від чого.
- `repository/` повертає прості об'єкти й не залежить від api/service/domain.
- `server.js` — єдине місце, яке знає про всі шари й з'єднує їх.

### Заборонені зв'язки

- `api/` не звертається напряму до БД чи `repository/`: вся логіка в `service/`.
- `service/` не імпортує `express` і не використовує `req`/`res`.
- `domain/` не імпортує нічого з `service/`, `api/`, `repository/`.
- `repository/` не імпортує `service/` та `api/`.
- Жоден шар не звертається вгору.
- Контекст не читає таблиці іншого контексту напряму, лише через його service.

## Наслідки

- Юніт-тести `service/` працюють без SQLite та HTTP (in-memory репозиторій).
- Додавання нового контексту (Orders, Users) — нові файли в тих самих шарах.
- Трохи більше файлів і мапінгу (row → domain → DTO), ніж у простому `server.js`.
