# ADR 0003: Стиль REST API та модель помилок

- **Статус:** Прийнято
- **Дата:** 2026-11-21

## Контекст

Потрібен єдиний стиль API й один формат помилок, щоб клієнт (і майбутні практичні з ретраями та observability) міг однаково обробляти відповіді. Джерело істини — `docs/api/openapi.yaml`.

## Рішення

### Стиль REST

- Контекст Catalog, сутність Product. Маршрут залишається `/items` (таблиця `items`, клієнт з практичної 1), як зафіксовано в глосарії (`docs/domain/glossary.md`, розділ 7). Перейменування в `/products` можливе окремим рішенням.
- JSON у запитах і відповідях; імена полів у `camelCase`.
- Методи: `GET /items`, `POST /items`, `GET /items/{id}`, `PATCH /items/{id}` (часткове оновлення), `DELETE /items/{id}`, `GET /health`.
- `id` — додатне ціле число. `POST` повертає заголовок `Location: /items/{id}`.
- Тіло запиту — окремі DTO (`CreateProductRequest`, `UpdateProductRequest`), які не збігаються з доменною сутністю; зайві поля (зокрема `id`) ігноруються.

### Політика статус-кодів

| Код | Коли |
|---|---|
| 200 | Успішні `GET` та `PATCH` |
| 201 | Успішний `POST` (створено) |
| 204 | Успішний `DELETE`, тіла немає |
| 400 | Невалідне тіло, некоректний `id`, зламаний JSON |
| 404 | Ресурс або маршрут не знайдено |
| 413 | Занадто велике тіло запиту |
| 500 | Непередбачена помилка сервера |

### Єдиний формат помилки (`ErrorResponse`)

```json
{
  "error": "ValidationError",
  "code": "VALIDATION_FAILED",
  "details": [{ "field": "name", "message": "Назва обов’язкова" }]
}
```

- `error` — категорія: `ValidationError`, `NotFound`, `BadRequest`, `InternalError`.
- `code` — стабільний машинозчитуваний код: `VALIDATION_FAILED`, `PRODUCT_NOT_FOUND`, `ROUTE_NOT_FOUND`, `INVALID_JSON`, `PAYLOAD_TOO_LARGE`, `INTERNAL_ERROR`.
- `details` — необов'язковий масив `{ field, message }`. Тексти `message` призначені для людини й можуть змінюватися, а клієнт спирається на `code`.
- Внутрішні подробності (стек, SQL) у відповідь не потрапляють, вони лише логуються на сервері.
- На практичній 5 до формату буде додано `requestId` (`X-Request-Id`).

### Валідація Product

- `name` — обов'язкове, непорожній рядок (після trim), до 200 символів.
- `price` — обов'язкове, число ≥ 0 (рядок `"10"` не приймається).
- `stock` — необов'язкове, ціле ≥ 0, за замовчуванням 0.
- `description` — необов'язкове, рядок до 2000 символів, за замовчуванням порожній.
- `PATCH` вимагає хоча б одне з полів.

### `GET /health`

Повертає `200` і текст `ok`. У практичній 5 буде змінено на `{ "status": "ok" }`.

### Відповідність OpenAPI

Будь-яка зміна ендпоінтів, статусів чи DTO вноситься в код і в `openapi.yaml` в одному pull request. Специфікацію перевіряємо в Swagger Editor.

## Наслідки

- Клієнт обробляє всі помилки однаково, спираючись на `code`.
- Ендпоінти трохи відхиляються від суворого CRUD із завдання: додано `400` для некоректного `id` в `GET`/`PATCH`/`DELETE`.
- Мінус: `Product` має більше полів, ніж початкова таблиця `items(id, name)`. Для цього БД розширюється міграцією при старті (нові колонки зі значеннями за замовчуванням).
